# Animal Crossing: New Horizons (`01006F8002326000`)

Update 3.0.3 (v2228224) over the base game, with the Happy Home Paradise add-on mounted. SDK 20.5.4. Nintendo EPD's own engine (code name Park; sead / agl / gsys, NintendoWare G3d / Ui2d / Vfx2 / Atk / Font, Havok, Pia and NEX for local and online play) on NVN. Modules `main`, `subsdk0` (the SDK's movie library) and `sdk`. Plays on the iPhone; 30 fps, as on the Switch.

On the Mac: a new game through Tom Nook's counter (name entry on the game's own keyboard, birthday, look, hemisphere, island choice), the in-flight movie with its sound, the island's creation and the arrival (Timmy's welcome, the player at the dock under control); no red line but the ones below. 1.85 GB resident and 1.15 GB of Metal allocations at the dock.

| `shader_groups` `/Shader/` `/System/` `/Effect/` `/Model/` `/Layout/` `/Swkbd/` | `game.tsv` | see [Files and shaders](#files-and-shaders) |

Render conditions, which the host evaluates for every game ([Conditional rendering evaluated at replay](../../../docs/reference/rendering.md#conditional-rendering-evaluated-at-replay); until 2026-11-12 the profile key `render_cond`): the game wraps its clears in render conditions that skip a target nothing drew into since its last clear, as Tears of the Kingdom does ([0100F2C0115B6000](../0100F2C0115B6000/README.md)). Without the key, four clear-only passes wiped the composite before the window copy at frame 900, and every frame came out black (the island probe and the loading icon were drawn into render targets).

## Rewriter

- **Resolved: a `B()` assertion at a spin wait, a branch into the patch area beyond the ±128 MB a `b` reaches.** Its `main` was the first module to put branches out of range of the patch area: 63 MB of text and 51 halfword jump tables (`ldrh wE, [xT, xI, lsl #1]; …; adr x18, #L; add x18, x18, xE, lsl #2; br x18`). Each got a landing pad for every one of the 65,536 values an entry can hold (768 KB a table), whatever the switch's size: 40 MB, and the spin-wait stubs placed after them were out of reach. The rewriter now pads only up to a table's largest entry (`half_pads`, from the [jump solver](../../../docs/reference/rewriter.md#jump-tables-proved-over-control-flow)'s table); 7 of the 51 could not be read then and kept all 65,536. The patch area went from 42 MB to 7.9 MB.
- The spin-wait search through stores finds 166 loops in `main` (162 before), and the movie library's thread loop is wider in `subsdk0` ([development.md, Power](../../../docs/development.md#power)).

## Threads

- **Resolved: a black screen with the plane icon for 77 s after the opening movie** (also about 40 s of the same at boot), the CPU nearly idle. `SaveProc` yielded about 2,600 times a second, the power line's top yielder with as many back-off sleeps. The thread was working, not waiting: its grid walks over the new island (`main+0x157d020`) call `nn::os::YieldThread` once per cell, and the back-off made each yield a 250 µs sleep. A yield whose caller's x19–x28 changed since the last one now counts as progress and returns at once (`thr_yield` in `hle_thread.c`). The island now shows about 10 s after the movie, as with `DM_YIELD_BACKOFF=0`. A temporary log of which of x19–x28 move at each yield, per thread, told the working loops from the polls.

## Services

- **Resolved: abort in `sm::Initialize` under `sf::hipc::InitializeHipcServiceResolution`, right after the first frames** (from `main+0x5b8198`). `main` links its own clients of `olsc:u` (cloud save data backup settings) and `npns` (push notifications), which talk HIPC through `sm` and `svcSendSyncRequest`. For each user the game asks whether backup is on and switches it off where it is (`main+0x2809c8c`); a failed connect aborts as well. `hle_sf.c` takes over the SDK's HIPC client entry points (`InitializeHipcServiceResolution`, `ConnectToHipcService`, `SendSyncRequest`, `CloseClientSessionHandle` and the control requests `QueryPointerBufferSize`, `ConvertSessionToDomain`, `DuplicateSession(Ex)`): `olsc:u` gets a host session, and every request on it succeeds with zeroed output, which reads as backup off for every user. Any other name is refused with a red line, as `sm` refuses a service nobody registered (`npns` was never connected). `DM_SF_TRACE=1` dumps each request.
- **Current: device save data.** 3.0.3's `main` mounts no account save data; the island is in device save data (`MountDeviceSaveData`, `GetDeviceSaveDataSize`, `ExtendDeviceSaveData`), which the host gives the account save's host directory and transaction (one player). A second mount name over a save already mounted shares that mount's transaction (`mount_ex`); it used to clone the committed directory again, over the first name's pending writes. Also `fs::Commit` with a `CommitOption` (its one flag clears the restore flag) and `GetSaveDataRestoreFlag` (never restored from a backup). A game whose `main` imports `MountSaveData` too gets a device save of its own (Mario Kart 8 Deluxe, [0100152000022000](../0100152000022000/README.md)); this game does not, so its islands stay where they are.
- **Resolved (PR #25): `fs::Commit(const char* const*, int)`, the mount-list overload.** The SDK's own code opened fsp-srv and aborted, leaving the save writes uncommitted. The host commits the list as one transaction when every name is the same host save; cache and temporary storage in the list are skipped, and a list of two separate saves is refused without committing either.
- Found in `main`'s imports before the first boot: the adjustable user clock (`time::AdjustableUserSystemClock::GetCurrentTime`, which the game's days follow) reads the time service's shared memory in the SDK (`MonotonicSystemClock::GetCurrentTime`, `sdk+0x4421cc`), which the host never maps, so it is the host's clock, as the user clock; `time::GetStandardSteadyClockCurrentTimePoint`, the free-function form of the steady clock; `oe::GetRegionCode` (from the language: Japan, the Americas, Europe or Hong Kong / Taiwan / Korea); the SDK 20 album calls `SaveAndShareScreenshot` with a share ID and `GetSharePostedLastUrl` (no album: they fail).

## Saves

- A save is not reached on the Mac: the game first saves when the player sleeps at the end of the first day (the `−` menu says "You can't save right now." before that). Until then it only probes for `main.dat`, `mainHeader.dat` and `Moved/personal.dat` in its device save data.

## Movies

- The in-flight movie `Movie/OpeningMovie.webm` is VP9 1080p with Vorbis, demuxed by `movie::Extractor` and decoded on the host (`hle_movie.c`).
- **Resolved: the movie showed as a black screen with the loading icon, one picture every few seconds, while its sound decoder kept up.** The player holds every output it is offered (16 of 16 video, 59 of 64 audio), so how far its extractor can get ahead of the picture on screen is the video slots plus the 4 queued packets. With 8 video slots that was 0.4 s, and the audio behind the next video packet, whose clock the player follows, ran dry: 86 pictures in 25 s. With 16 or 32 slots all 1,960 play at 30 fps. A video decoder now has 16 (`MD_NOUT_VIDEO`); a slot is allocated when first used, so the 8 more cost 24 MB of NV12 at 1080p only in a player that holds them all.

## Screen shape (`DM_SCREEN_ASPECT`, current)

With `DM_SCREEN_ASPECT=1.43` (launcher setting *Picture shape*, offered because the profile has `screen_aspect on`; the host side is Breath of the Wild's, [its note](../01007EF00011E000/README.md#screen-shape-dm_screen_aspect-current)) the game renders a 1920x1344 picture of the screen's own shape instead of a 16:9 one: 16:9's sides with more above and below, the layouts in their own shape, and their edge widgets at the taller screen's edges. The stubs in `patches.py` (3.0.3 `main` only) each take one bit of `DM_SCREEN_ASPECT_SITES`:

- **Sizes** (bits 0-4, 7, 8). The platform config (vtable `main+0x47fa0e0`, no RTTI) hands out the display size three ways: the graphics create arg (`main+0x5c9b44`: +0x60 the display size from the table at `main+0x4076728`, +0x20 1280x720), slot 7's static display size and slot 8's static 1280.0 x 720.0, and slot 3's arg +0x14. Each takes the screen's shape (the game's own 1920-wide value scaled by the output's width and height in integers: 1920 x 1344 at 1.43). Every frame `main+0x1527ebc` reads the resolution table's entry into the display buffer's crop and the 3D views' render scale: without its two loads (`main+0x1527f00`, `main+0x1527f2c`) the 1920x1344 window was cropped back to its top 1920x1080. The layouts' DrawInfo takes the framebuffer's size at `main+0x31cee60` / `main+0x31cee9c` for nn::ui2d's scissors and captures. The display buffer object's own size (`[main+0x59ea928]` +0x3a8 / +0x3ac, what the render scale divides by and what the screen-mapping code reads) is the picture's output size in every frame (`main+0x1527f10`), not the window's: in a window that holds every shape the buffer is the union, and the game would render a picture of the buffer's shape for the present to crop (a phone lying down showed its standing picture's upper half, stretched). After a turn the game rebuilds its views' projection matrices every frame from the aspect the views were built with at start (`main+0x37e5968`'s objects keep it); the adapter's `_dm_view_matrix` records that start aspect from the first projection it builds (state +0x1cc) and gives a projection carrying it the current picture's aspect instead, so a turned picture keeps the drawing a game started in that orientation has (a Mac trace of the projection's inputs showed the aspect stuck at the start shape and the viewport already the new one: the scene squeezed between them).
- **Tall pictures** (the output narrows). The game's layout tables stop at a display height of 2048: 0.9375 and 0.936 start, 0.935 does not. A phone's upper half (0.92) asks for 2088, so `loader.c` narrows the output instead of growing it: 1880x2040 keeps the shape to 0.17%, and the layout space is 1280x1389 (state +0x64 is the output's width, which every size above scales by). Two fixes of the game's own code come with it, at every shape: the fixed heap (cSys, the size table at `main+0x404d658`) grows by 32 MB (168.9 to 200.9), because the taller display's capture buffers and layers outgrow it (an allocation at `main+0x37c6a10` fails); and the capture manager (`main+0x3848e10`) no longer takes its destroy path, which clears `[x22+0xa0]` at `main+0x3849774` and leaves the null the frame reads at `main+0x38497c0` / `main+0x38497dc` (fault address 0x85 at `main+0x38497e0`; the branch to `main+0x38497a8` is the path a frame without a match takes).
- **The view** (bit 5). The island camera keeps its vertical angle in radians at +0x2cc (0.384, 22 degrees) and reads it twice (`main+0x7a895c`, `main+0x7a89a8`); both reads, and the other camera path's half angle (`main+0x386a7a0`), are widened to 2 atan(tan(fovy/2) k), k = (16/9) / ratio. The aspect already follows the taller viewport, so before this the picture kept the vertical angle and lost a fifth of each side.
- **Layouts' projection** (bit 6). `nn::ui2d::DrawInfo::SetProjectionMtx` (`main+0x265100`) gets the layouts' perspective projection of a 16:9 rectangle (m0 1.545, m5 2.747, fovy 40 degrees); its y row is divided by the vertical stretch (layout height / 720) before the return, so layouts keep their shape, centred. Only a projection within 5% of 16:9 is divided: the game copies a DrawInfo's projection into another, and without the check the title's layouts were divided twice.
- **Edges and backgrounds** (bit 9, `duo_anchor.c`, run after `nn::ui2d::Pane::Calculate` has computed a pane's global matrix, `main+0x27d570`). The game's panes are its own classes (no RTTI): what draws is told by its vtable's DrawSelf (slot 21) against `nn::ui2d::Pane::DrawSelf` (`main+0x27e2c8`, empty). A full-screen or full-height background leaf is stretched to the taller screen; a widget (the topmost pane of its chain that is not a null pane, alignment or layout-sized container) beyond 230 units from the middle towards a corner (|x| 400 or more), or 270 nearer the middle, moves out by the extra half-height with its children. A widget as wide as 60% of the layout is a panel, not an edge widget, and stays where its dialog has it: the keyboard's backing is 1240 of 1920 wide across the bottom of the name dialog, and moving it alone tore the keyboard, the keys above it sitting in the layout's middle and staying. Layouts are 1920x1080 (793 of 959) or 1280x720; the distances are in 720 units and scaled by the root pane's size. Layouts placed by their root (balloons over characters) are left alone. The text-entry keyboard docks the whole interface to the picture's bottom by moving the layouts' projection, not their panes: while it is up, the screen UI manager's projection getter (`main+0x5ce924`, `_dm_view_ui_override`) adds the picture's extra half-height to the projection's y translation, and the name card, the keys and the bottom bar (globe / ABC / Space / Confirm) stay one piece at the picture's bottom, with the scene above them; the edge rule leaves the keyboard's bar where the layout has it while the dock is on (`docked` in `duo_anchor.c`), since moving it as well would take it below the picture. Three stamps arm the dock: a key pane (`L_BtnNml_01`, state +0xb0) and the language list's panes (`N_BgMask`, `N_R`, +0x274) when they are calculated, and the dialog's name card (`W_BaseL_`, +0x1f0) when it is created, which is also the dock's own hold: the dock stays 36 presents after the last of them. The hold carries it through the keyboard's first frame (the card is calculated before the keys) and through the switch to the language list (the keys are gone and the list's rows are not drawn yet). The touch mapping subtracts the dock (`ui_y` in `hle_touch.c` reads state +0x1c4), and scissor rectangles move with it in layout units (`_dm_view_clip`, `main+0x31d44b0`). A 16:9 picture needs none of this: its keyboard already sits at the picture's bottom, and `state+0x80` (the layout shift) is 0 there, so no stamp is written and the dock stays off. `_duo_anchor` (patches.py) is the code of `duo_anchor.c` built with the command in the comment above it.

Checked on a Mac (M1, macOS 27, headless, an island save) against 16:9: the 3D view keeps 16:9's sides and shows more above and below; the title's version, press-A and settings lines, the island's ZL icon, clock, minimap and button guides sit at the new edges; the pockets, the phone (its backdrop's light band stretched) and the save dialog keep their shape. At 0.92 (the iPhone's upper half) an island save shows the same: the ZL icon, clock and minimap at the picture's corners, the phone and the map inside the 16:9 band, and the name entry's keyboard at the picture's bottom — the text field, the keys and the bottom bar (globe / ABC / Space / Confirm) one piece, the scene above them. The row of button hints (L← R→ Ⓨ X Cancel A Select) follows them to the picture's bottom. At 2.17 the keyboard keeps its 16:9 place unchanged. On an iPhone Duo (iOS 27.1) an earlier build of this looked right to its player. Open: an NPC's dialog box stays at its 16:9 place (-320), not at the taller screen's bottom edge; the phone's blurred backdrop shows a hard edge at its top left.

The profile whose stubs read the union window (`screen_union`) also follows a 19.5:9 phone's two shapes: `0.92` standing up, the picture's upper half ([iPhone portrait](#iphone-portrait-current)), and `2.17` lying down, the screen's own shape ([iPhone landscape](#iphone-landscape-current)). No other ratio is adapted; iOS `auto` resolves the two from the window, and `DM_SCREEN_ASPECT=0.92` / `2.17` set them by hand.

## iPhone portrait (current)

A phone standing up shows the game's picture in the upper half of the window and the companion band in the lower half: `dm/ios/Sources/DmLayout.h` splits the window at its midpoint, and the picture is fitted into that half. *Picture shape* `auto` asks for the half's own shape only on a 19.5:9 phone (twice the window's width / its height: 0.92), so the fitted picture fills the half exactly; a 375x667 phone's 1.12 and an iPad's 1.39 are outside the profile's bands, so those keep 16:9: its background covers the area with nothing cropped and nothing stretched. The game's own layouts keep 16:9, centred in the picture (the layouts' projection divides its y row by the vertical stretch, above), so its HUD and menus are not stretched either; the touch screen maps a touch on the taller picture back onto that centred rectangle (`ui_y` in `hle_touch.c`), so a control is hit where it is drawn. A manual `DM_SCREEN_ASPECT` that does not match the half keeps its whole picture and leaves bars instead of cropping it. The picture never takes more than half the window, so the band keeps the other half; a fold sets both edges itself.

**The picture follows the phone turning.** The game builds its window textures once, at start, from the display size its platform config hands it, and a console mode change only moves the picture's crop. The iPhone app therefore has the host give it a window that holds every shape the profile's range allows (`DM_SCREEN_ASPECT_UNION`: 1920x2048, [A window that holds every picture shape](../../../docs/reference/rendering.md#a-window-that-holds-every-picture-shape-so-a-phone-may-turn)), which costs the portrait shape's pixels while the phone lies down. On a turn `dm_screen_shape` (`loader.c`) writes the new picture's fields into a request block, and the frame stub at the first read of the state page in each frame (`main+0x1527f00`, `patches.py`) copies them, so no frame mixes two shapes (a change landing between a frame's reads cleared an old-width strip of a new-size target), and the present takes the picture's shape from the crop the frame was queued with (`present_picture_fit`, `nvn_mtl.m`), covering the drawable when the picture's fit is Fill so the one frame before the new shape lands does not shrink into a letterboxed strip. The HUD's edge parameters and the scene's projection follow the same read: a phone standing up fills its upper half (0.92) and lying down fills the screen (2.17), whichever orientation the game was started in. The picture's output is capped to the pixels of the view it is shown in (`DM_SCREEN_ASPECT_PX`, `dm_screen_shape_px`; the 1920-wide space is a coordinate space): a standing phone drew 1880x2040 into a 1206x1311 view, 2.4 times the pixels, which made a turn's frames 2.2 times the lying-down ones. Seen on a device: the turn both ways without black bars, and a scene drawn as a game started in that orientation draws it.

**A phone standing up is handheld, so the game's own keyboard takes touches.** The profile sets no `op_mode`, so the game starts docked and the host hands it no touch points (`touch_read` in `hle_hid.c`), which leaves the game's keyboard unreachable. The front end therefore switches the console mode by the screen's orientation while no TV shows the picture (`followOrientation` in `front_ios.m`): standing up it goes handheld and lying down it returns to the mode the player had, a choice made in the in-game menu included. The game reads touches in both modes, so nothing else has to change, and the switch is the console mode change notification the game watches, so it follows while it runs. With a window that holds every shape the size table stays on its docked entry (bit 10 of the sites) while the console is handheld, so the picture is drawn at the output's own size standing up; a manual `DM_SCREEN_ASPECT` without the union (the Mac) keeps handheld's 1280x720. *Console mode* in the in-game menu (or `DM_OPMODE=0` in `Documents/env.txt`) still works for a phone lying down.

### The pad

The pad is this profile's own (`portrait_pad spaced`; another profile keeps the overlay's single row in its band and 2D in the menu). Every gap between neighbouring keys is ten points: the shoulders, the stick clicks, the ABXY keys and the D-pad's arms are all spaced by it.

**Standing up** (`DmGamepad.m`, the geometry in `DmLayout.h`) the controls make two rows in the band: the left stick and the ABXY diamond in the upper one at 50 % of its height, the D-pad and the right stick in the lower one at 82.5 %, each in a column at a quarter and three quarters of the band's width. The rows leave the top of the band to the panel and the lower one clear of the home indicator. The ABXY keys keep the landscape's proportions (key distance 50 u, key radius 27 u, so their outer edge is the stick's ring), the D-pad is drawn at 0.85 of that ring with the arms' 17:48 proportion, and the right stick — which the landscape pad leaves undrawn (a touch in the right third holds it) — has a ring of its own at that same 0.85 and is pressed in it. The unit comes from the gap between the rows, so each device gets the largest size its rows allow (u = 0.704 on a 390 x 844 band).

**Lying down** the three clusters share one line and the margins the shoulders' own circles keep to the screen's edge: the stick's ring and the diamond's outer edge sit 18 u from the side and 14 u from the top and bottom (centres at 95 u and H − 91 u, where the overlay had 81 u and H − 82 u), and the D-pad's centre at 264 u joins that line. The stick clicks sit on the line between the two shoulders, in both orientations.

Every shoulder is drawn at the ABXY key's own radius, so the top row and the diamond read as one size; its circle keeps the margin it had to the edge (18 u on a lying phone, 17.8 pt on a standing one) and the two keys of a column stay the gap apart they had. The `−`, the menu gear and `+` keep the margin the shoulders' circles keep to the top edge, so their top edge sits on the shoulders' top edge — 9.3 pt lower than the overlay's row on a standing phone, 5.4 pt on a lying one — and the frame-rate counter follows the gear, six points below its circle. `K_TOP_LIFT` takes that whole top row — the shoulders, the stick clicks, the pills, the gear and the counter — five points higher, standing or lying down (a device, 2026-11-20). The in-game menu offers 3D and Tap only. The choice is the run's own: this profile neither stores it nor reads a stored one, so every start returns to the profile's `pad_layout`. A triple tap on the home indicator switches between 3D and the game's own touch screen, and back: the home indicator's own length — a share of the screen's short side (about 141 points on a 402-point phone, 154 on a 440-point one), twice that lying down — plus 10 points of the finger's slop around it. Standing up the strip stops at the safe area's bottom edge (34 points; its own 5 are too thin for a finger), so the band's bar above it keeps its tabs' taps — before, the strip reached into the bar and the Critterpedia and DIY tabs there were hard to hit; lying down it takes the strip plus the slop, where no panel sits under it. The pad takes those taps itself so the panel below cannot swallow them. Three taps half a second apart at most, each swallowed so a mis-aimed one cannot become a game touch, and only where no control took the touch, so the D-pad and the right stick keep their own. Tap here is the band's panel, not the game's touch screen, so it stays available in either console mode — a TV takes neither the menu's Tap nor the triple tap away. A hint sits on the indicator's top edge for the first ten seconds of each start.

The Duo harness (`dm/ios/tests/duo`) covers the pad without the panel: both orientations' anchors, the right stick's ring (drawn at the D-pad's scale standing up, the right third lying down), that a touch in it drives the stick, the keys' and the hit targets' sizes, and that a touch in the band on no control passes through to the panel below.

### The companion band

The band under the picture is filled by Eden Duo's ACNH companion: the island map, the pockets (slot by slot, with the game's own item menu and a move to another slot), the Critterpedia, DIY, Today and the NookPhone, drawn from the module's live outputs by a data-driven SwiftUI renderer. Its manifest and authored strings are the ones vendored in `dm/third_party/eden_duo` (GPL-3.0-or-later: a build that includes the companion is distributed under that license, [NOTICES-nxnative.md](../../third_party/eden_duo/NOTICES-nxnative.md)). This profile's `companion.json` opts it in: `build_ipa.sh` then bundles `dm/companion-ui.json` (built from the MSBT strings), the profile's build rows and input gates and the notices, and defines `DM_COMPANION`; `companion.mk` adds the module's and Zstandard's sources to the host, and the two Swift files of the renderer join the target, so no other game's app carries any of it (`build_ipa.sh` excludes them there).

The module reads the guest through the host's own heap access (`dm_companion_guest_read` in `hle_companion.c` uses `hle_svc.c`'s locked range and copy rather than a bare `vm_read`, so a concurrent `SetHeapSize` cannot turn a bounds check into a use-after-free), finds the game's functions by their instruction words and closes the domain a mismatch belongs to. Its writes are the pockets' own item moves and exchanges, gated on the build ID (`write_builds`); the rest of the interface is read-only. The view sits under the pad, which keeps the taps that land on a key and passes the others through (`DmGamepad.m hitTest`); a phone lying down, or a window without a split, hides it.

A pocket move reaches the save the game writes, so a snapshot taken before reorganizing is the way back: the save sync keeps its last ten backups of each side (`save_sync.c`, unchanged), and restoring one needs the game fully quit.

## Adaptive view consistency (current)

On a taller picture the game caches projections and screen rectangles that a change of shape has to invalidate. The adapter in `view.s` (built to position-independent ARM64 by `gen_view_stubs.py`, licensed MIT-0 in `view.LICENSE`) is registered by `FRAME_STEP` for 3.0.3 `main` only: 21 hooks and 29 caches refresh cached projections, follow the current perspective in scissors and captures, widen field ranges and near-plane unprojection, and dock the inline keyboard and footer. It shares the frame step state page with `screen_shape` and needs no host state of its own.

`main+0x265140` is the single `ret` of `nn::ui2d::DrawInfo::SetProjectionMtx`. The chained stub there (the upstream y-row division, then a dock of the projection) does not run in this build: its 16:9 test reads m0 and m5 of copies that are already band-shaped, so it never divides, and the keyboard docks through the panes instead ([Edges and backgrounds](#screen-shape-dm_screen_aspect-current)). `main+0x27d4c0` forces the footer subtree dirty at `Pane::Calculate` entry and `main+0x27d570` runs `duo_calc` after `CalculateGlobalMatrix`: the two were disassembled and coexist. `_dm_view_footer_y` takes its adjustment away while the keyboard is up; the row of button hints it matches (`N_Align_`, 1810x100) is drawn from a layout of its own, and it was seen to keep that layout's place whatever was written to the row's own panes or to that layout's root, so the row does not come down with the keyboard.

The adapter follows the host's `DM_SCREEN_ASPECT` through `dm_fps_state +0x58`. **Its lower bound is a display height of 2048** (a layout height of 1365): the game's layout tables have no entry for a taller display, and both the actor manager (`main+0x7a1ba0` → `main+0x1961090`, fault address 0x8) and the capture manager (`main+0x38497e0`, fault address 0x85) read through the null they get. Headless on a Mac at 3.0.3 `main`, 0.9375 and 0.936 start and run, 0.935 does not; the threshold is the display size's (bits 4 and 7 of `DM_SCREEN_ASPECT_SITES` alone still crash, the layout size alone is harmless), and the layout height does not matter (1389 and 1500 both boot with a display height of 2048). The host therefore narrows the output rather than growing it past 2048: 0.92 renders 1880x2040. Above 16:9 the range is open: 2.167 (a 19.5:9 phone lying down) ran 120 s headless. The shape may change while the game runs (the iPhone app's window holds every shape, [iPhone portrait](#iphone-portrait-current)); ratios outside the profile's range and an iPhone Duo's fold are not handled. At `+0x58 = 0` (16:9) every adapter stub runs the original instructions.

The frame stamps are values in the free part of the state page, with no host pointer: `+0xa8` is the host's present counter (`dm_guest_frame_tick`, `hle_os.c`, one relaxed store each present), `+0xb0` the keyboard's stamp (the adapter's `keyboard_frame` writes it through `Ltouch_stamp` (`x17` = 8), and `duo_calc` writes the present counter's value when a key of the game's keyboard is calculated) and `+0xb8` a touch panel's, written by `touch_page`. `Lrecent_keyboard` subtracts the first two, so "the inline keyboard rendered in the last two presents" needs no host state. `keyboard_window` keeps its own stamp at `+0x38`, which nothing reads: AnimalDuo's touch-context (bit 3) was not ported.

The layouts' fit in `_dm_view_ui_override` / `_dm_view_panel_projection` (`Lscreen_projection`) keeps the game's 16:9 layouts at their own scale, centred in the taller picture: the projection's y scale is divided by the picture's vertical stretch. A picture narrower than 16:9 then also keeps `duo_anchor`'s edge widgets where the layouts have them (`loader.c` clears its shift): the fitted layouts already hold them, and moving them as well put them past the picture (a device, 2026-11-20 — the title's version line, a chat balloon and the camera's frame were the visible ones). The fit follows **bit 11** of `DM_SCREEN_ASPECT_SITES` (on by default); clearing it leaves every drawing with the game's own projection over the whole picture (the layouts stretch with it), which `DM_SCREEN_ASPECT_SITES=0xfffff7ff` in `Documents/env.txt` shows on a device. The keyboard's dock in `_dm_view_ui_override` still moves the projection with bit 11 clear; the `DrawInfo` boundary's copy keeps its own place.

Seen on an iPhone standing up (0.92, 2026-11-20) with the fit and the edge widgets' move both on: the title screen's version line sat high in the picture beside the performance HUD and the picture's bottom edge showed no layout; a player's chat balloon sat at the character's feet with its name plate overlapping it; the camera mode's frame corners, hints and zoom column stayed in the picture's middle. With that move off (an earlier app and `DM_SCREEN_ASPECT_SITES=0xfffff5ff`) the layouts kept 16:9, centred, the scene still filled the picture's portrait shape, and the player found the screen as it should be; a picture narrower than 16:9 now clears the move itself, so no switch is needed.
